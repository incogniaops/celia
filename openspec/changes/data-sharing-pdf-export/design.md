# Design

## Context

See proposal.md for motivation. Relevant current state:

- `app/dashboard_data.py` already computes everything the report's two summary boxes and AGP chart need: `get_glucose_summary_stats` (average mg/dL, GMI %, GMI mmol/mol, %CV, `band_percentages`) and `get_agp_percentile_bands` (p5/p25/median/p75/p95 per 5-minute bucket of the day, via `_agp_bucket_minute`). Neither needs to change.
- There is no existing per-day grouping of glucose readings by time-of-day (the daily-profile grid's data shape). `get_monthly_glucose_calendar` groups by day but only keeps each day's *average*, not its shape; `get_agp_percentile_bands` groups by time-of-day but collapses *across* days. A new function is needed that groups `get_glucose_trend`'s readings by calendar day, each day keeping its own `(time_of_day, value)` points, reusing `get_glucose_trend` rather than issuing a new query.
- `app/routers/dashboard.py`'s `_resolve_range`/`_dashboard_context` already define how `start`/`end` query parameters become the inclusive datetime range used everywhere else on the dashboard; the export route reuses `_resolve_range` so the PDF's range-resolution rules (defaults, swapped start/end, Mexico_City "today") stay identical to the dashboard's.
- The Containerfile is a two-stage build (builder installs Python deps to `/install`, final stage copies them in, non-root `celia` user, Debian slim base) with an existing pattern for optional corporate-proxy trust (`--secret id=corp_ca_cert`) during `pip install`. A LaTeX engine is a new kind of build-time dependency, not a Python package.

## Goals / Non-Goals

**Goals:**
- Produce a single PDF, typeset with real LaTeX (not an HTML-to-PDF conversion), for one date range, reusing celia's existing computed figures exactly.
- Keep the container image's size growth and the deployment's runtime network dependency both small, given this is a single-user homelab deployment, not a service with elastic infrastructure.
- Reuse the existing `start`/`end` range-resolution logic rather than building a parallel one for the export route.

**Non-Goals:**
- Any clinical interpretation, pattern detection, or recommendation text (see proposal.md's deliberate-deviations list).
- A share link, access control, or revocation (removed from the spec; see proposal.md).
- Localising the report itself beyond celia's existing UK-English/Spanish-proper-noun convention -- the report is for the user's own doctors, already written in whichever language the rest of celia is.
- Making the daily-profile grid's per-day rendering pixel-identical to Abbott's; "modelled on" means the same sections and layout intent, not a visual clone.

## Decisions

**Tectonic, invoked as a subprocess over a `.tex` file, not a Python LaTeX binding.** Tectonic has no stable first-party Python binding; shelling out to its CLI (`tectonic <file>.tex --outdir <dir>`) is the simple, well-supported path, consistent with the project's existing preference for stdlib/subprocess-level solutions over adding dependencies where a CLI tool already does the job cleanly.

**Jinja2 renders the `.tex` source, with `\BLOCK{ }`/`\VAR{ }`/`\#{ }` custom delimiters, not doubled parentheses.** celia already uses Jinja2 for HTML; reusing it for the `.tex` template avoids a second templating approach. Jinja2's default `{{ }}`/`{% %}` delimiters collide with LaTeX's own `{`/`}`. The first implementation attempt used doubled-paren delimiters (block `((* *))`, variable `(( ))`) instead, but this broke on the template's own pgfplots coordinate lists: a literal `(` written immediately before a variable, as in `((x)),((y))` for a `(x,y)` coordinate pair, confused Jinja2's lexer (it balances parentheses to find where an expression such as a filter call ends) and raised `TemplateSyntaxError: unexpected ')'` -- caught by locally compiling a real AGP-chart coordinate list during implementation, before it reached the Containerfile. Switching to the word-prefixed brace delimiters `\BLOCK{ ... }`/`\VAR{ ... }`/`\#{ ... }` (the scheme documented in Jinja2's own LaTeX-templating recipe) resolved it, since these share no character with LaTeX's parentheses and so never collide with coordinate-list syntax. Free-text values that are not already-trusted literals (the user's own name, and the band-target strings like `<25%`, both of which contain characters LaTeX treats specially) are passed through a small `latex_escape` filter for LaTeX's reserved characters (`% & # $ _ { } ~ ^ \`); accented characters (Álvarez, México) do not need escaping, since Tectonic's engine is Unicode-aware (XeTeX-like) and consumes UTF-8 input directly, matching celia's existing "accent Spanish proper nouns" style rule without extra work.

**Time-in-range bar and the AGP chart are native LaTeX graphics (TikZ / pgfplots), not pre-rendered raster images.** This is the difference between "an editorial, LaTeX-typeset report" and "an HTML report saved as PDF" -- vector output, typeset alongside the surrounding text with consistent fonts. The stacked time-in-range bar is a handful of proportionally-sized filled TikZ rectangles (no pgfplots needed). The AGP chart is a `pgfplots` filled-band plot (`\addplot fill between`) fed `get_agp_percentile_bands`'s existing per-bucket p5/p25/median/p75/p95 values directly as coordinate data -- no new computation, just a different renderer than Chart.js.

**The daily-profile grid reuses the same per-day points as small pgfplots line plots, arranged in a LaTeX grid, one row per week (Monday-Sunday) -- matching `get_monthly_glucose_calendar`'s existing week-grid shape, not a new calendar layout.** A new `get_daily_glucose_profiles(db, start, end)` function in `dashboard_data.py` groups `get_glucose_trend`'s already-fetched readings by calendar day (each day keeping its own list of `(minute_of_day, value)` points, raw -- not bucketed, since a single day's worth of CGM readings is already sparse enough, roughly every 15 minutes, to plot directly), and reuses the same Monday-start week-grid construction `get_monthly_glucose_calendar` already does, so both calendars agree on how a date range maps onto week rows.

**Tectonic's package cache is warmed at image-build time, not left to fetch over the network at runtime -- by compiling the real template with synthetic sample data, not a separately hand-maintained throwaway document.** Tectonic normally fetches TeX Live package files on demand from a bundle and caches them locally; a homelab VM may not reliably have outbound internet at the moment a PDF is requested, and a report request is the wrong time to discover a missing package. The Containerfile's builder stage runs `app/pdf_export/warmup.py` (built-in synthetic data: a populated glucose summary, AGP bands, and a two-week daily-profile grid) through the same `render_tex` the real export route uses, then compiles that output once during `podman build` (which already assumes outbound network access, the same assumption `pip install` and the corporate CA secret-mount already make). A first implementation attempt used a separate, hand-written warm-up `.tex` document instead, and it drifted from the real template twice before this change was even committed: once on a mismatched `\documentclass` font-size option (`size11.clo` was never cached, so the real template's compile failed offline at runtime with a `File not found` error), and once on a missing `\usepgfplotslibrary{groupplots}` (the daily-profile grid's library, omitted from the stand-in document, again only surfacing as a runtime failure). Rendering the real template for warm-up makes this class of drift structurally impossible, since there is only one template to keep in sync with. The resulting cache directory is copied into the final image alongside the `tectonic` binary, owned by the existing non-root `celia` user. At runtime, generating a report is expected to need zero network access -- verified directly with `podman run --network none`.

**Large date ranges let LaTeX break pages naturally, rather than forcing a fixed number of week-rows per page.** A first implementation attempt forced a `\clearpage` every 4 week-rows; the user immediately flagged the result as "horrendo" (horrendous) when reviewing it in their browser -- a 30-day range (5 week-rows) was cut short at 4 rows regardless of how much room was left on the page, leaving most of page 1 blank *and* pushing the 5th row onto an almost-entirely-blank page 2. Each week-row is already its own self-contained `tikzpicture`/`groupplot` (an atomic LaTeX box that cannot itself split across a page break), so removing the forced `\clearpage` and letting LaTeX's normal paragraph-level pagination place each week-row lets it break only where a row genuinely does not fit -- a 30-day range now renders on a single page, and longer ranges (e.g. 90 days) still page-break, but only when actually necessary.

**Body font is Latin Modern Sans, loaded via `fontspec` by exact bundled `.otf` filename, not by font name.** The first rendered PDF used LaTeX's unstyled serif default (Computer Modern) and the user rejected it outright on sight ("la fuente es horrenda"). Tectonic's engine is XeTeX-based, so the standard way to change fonts is `fontspec`'s `\setmainfont{<name>}` -- but that failed here (`! Package fontspec Error: The font "Latin Modern Sans" cannot be found`), because by-name lookup relies on the OS's fontconfig database, and this sandboxed build has none (the "Fontconfig error: Cannot load default config file" warning seen since the very first warm-up compile, previously dismissed as harmless, was this exact gap surfacing early). The fix, confirmed empirically: `\setmainfont{lmsans10-regular.otf}[UprightFont=*, BoldFont=lmsans10-bold.otf, ...]` -- an exact `.otf` filename, which XeTeX resolves via kpathsea (TeX's own file-finding, independent of fontconfig) rather than by font-name lookup. The older 8-bit PostScript route (`\usepackage{helvet}` + `\renewcommand{\familydefault}{\sfdefault}`) was tried first and compiled without error but silently kept rendering serif text -- a second empirically-caught dead end, not a theoretical alternative dismissed on paper.

**Section layout is Abbott/LibreView-styled shaded panels (`tcolorbox`), not bare floating text.** The user's follow-up feedback ("el layout no se parece en absoluto al reporte de Abbott") named the gap directly: the real report's defining visual trait is that every section (time-in-range, glucose stats, AGP, daily grid) sits inside a light-grey, rounded-corner panel with a bold left-aligned title -- not text floating directly on a white page. `tcolorbox` (with the `most` library bundle, confirmed available in Tectonic's default package set) reproduces this directly: one `\tcbset{panel/.style={...}}` shared style for every section, and `tcbraster`'s `raster equal height` for the top two panels so they match height exactly like Abbott's, regardless of how much shorter the glucose-stats panel's content is than the time-in-range bar -- turning what was previously a jarring whitespace imbalance (see the pagination entry below) into ordinary-looking panel padding instead.

**The user's name comes from a new `PROFILE_NAME` environment variable, following A-09's existing precedent exactly.** `PROFILE_HEIGHT_M` and `PROFILE_BIRTH_DATE` already establish the pattern for fixed personal facts no ingestion source provides, kept out of source control (see docs/PS-CELIA-001's A-09). The report header's name is the same kind of fact, so it follows the same mechanism rather than introducing a different one (a config file, a database row, a CLI argument).

## Risks / Trade-offs

- **Compiling ~13 small pgfplots axes per week-row (up to 13 week-rows for a 90-day range) could make PDF generation noticeably slower than the sub-second dashboard page load.** → Acceptable for a single-user, on-demand export (not a page users wait on for every dashboard refresh); revisit only if real-world generation time becomes annoying in practice.
- **Tectonic's exact cache directory and offline-bundle behaviour were confirmed empirically during implementation, not just assumed.** On Linux (unlike macOS's `~/Library/Caches/TectonicProject.Tectonic`), Tectonic 0.17.0 caches to `$HOME/.cache/tectonic`; warming it once while trusting the corporate CA (the same CA the pip-install step already needs), then running with `--network none`, was verified to compile successfully with zero network access -- confirming the build-time warming decision above works as designed, not just in theory.
- **A LaTeX compilation can fail on unexpected input** (e.g. a future free-text field with characters the `latex_escape` filter doesn't yet cover). → Scope this change's escaping to the one free-text field that exists today (the user's own name from configuration, already trusted/fixed); broaden `latex_escape` if/when a new free-text field is ever added to the report.
